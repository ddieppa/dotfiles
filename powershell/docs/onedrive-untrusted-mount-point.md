# Fixing the "untrusted mount point" PowerShell startup error

## Symptom

Every time you open `pwsh` (or run almost any command), you see:

```
The path cannot be traversed because it contains an untrusted mount point. :
'C:\OneDrive\Documents\PowerShell\Microsoft.PowerShell_profile.ps1'.
```

The path may differ slightly depending on where Windows redirects your `Documents` folder. Common variants:

- `C:\OneDrive\Documents\PowerShell\Microsoft.PowerShell_profile.ps1`
- `C:\Users\<you>\OneDrive\Documents\PowerShell\Microsoft.PowerShell_profile.ps1`
- `C:\Users\<you>\OneDrive - <Tenant>\Documents\PowerShell\Microsoft.PowerShell_profile.ps1`

Either way, the file in the message is the path PowerShell uses for `$PROFILE.CurrentUserCurrentHost`.

## Root cause

Two things combine to produce the error:

1. **Your `$PROFILE` lives inside an OneDrive-synced folder.** Windows 11 redirects the user's `Documents` folder into OneDrive when "Backup" / "Known Folder Move" is enabled, so the per-user PowerShell profile ends up under a `OneDrive\…` path.
2. **The profile path itself is an NTFS reparse point** — most often a symbolic link (a previous installer in this repo created one pointing at `D:\dotfiles\powershell\Profile.ps1`), but it can also be a junction or any other reparse point.

Modern PowerShell on Windows 11 refuses to *traverse* reparse points whose target lives in a "less trusted" location than the link. OneDrive folders are explicitly considered untrusted because the cloud sync agent can swap their contents under PowerShell's feet. This protection is implemented in PowerShell itself (`PSResolveReparsePointToNonTraversable`) and surfaces as the "untrusted mount point" error before your profile body ever runs.

The error therefore is **not** a bug in `Profile.ps1`. It fires while pwsh is still resolving `$PROFILE` during startup.

### Why a previous installer made it worse

The earlier `install.ps1` in this repo did:

```powershell
New-Item -ItemType SymbolicLink -Path $PROFILE.CurrentUserCurrentHost `
    -Target 'D:\dotfiles\powershell\Profile.ps1' -Force
```

That created a symlink at `C:\OneDrive\Documents\PowerShell\Microsoft.PowerShell_profile.ps1` pointing at `D:\dotfiles\…`. Windows treats traversal from the OneDrive side to the `D:\` side as crossing a trust boundary, and refuses.

## The fix: stub files instead of symlinks

Replace each symlink under `$PROFILE` with a tiny **plain `.ps1` file** that dot-sources the real profile from this repo. A plain file is not a reparse point, so the traversal check never triggers. The dot-source then runs the real profile from `D:\dotfiles\…`, which lives outside any reparse boundary.

A stub looks like this:

```powershell
# Auto-generated by D:\dotfiles\powershell\install.ps1
# Loads the dotfiles profile. Edit Profile.ps1 in the dotfiles repo, not this stub.
. 'D:\dotfiles\powershell\Profile.ps1'
```

### Why this works

| Property                     | Symlink at OneDrive `$PROFILE` | Plain `.ps1` stub at OneDrive `$PROFILE` |
| ---------------------------- | ------------------------------ | ---------------------------------------- |
| Reparse point on disk        | Yes                            | No                                       |
| Triggers untrusted-mount check | Yes (blocked)                | No (loads normally)                      |
| Forwards to dotfiles repo    | Implicit (via target)          | Explicit (`. '<path>'`)                  |
| Survives OneDrive sync       | Sync engine may rewrite link   | Plain file — sync just copies bytes      |
| Requires admin to create     | Yes (without Developer Mode)   | No                                       |

The trade-off is that the stub is a real file in `Documents`, so it gets backed up by OneDrive like any other file. That's harmless — it's two lines of text.

## Running the fix

From any pwsh session:

```powershell
& D:\dotfiles\powershell\install.ps1
```

You should see something like:

```
Removed existing symlink at C:\OneDrive\Documents\PowerShell\Microsoft.PowerShell_profile.ps1
Installed stub at C:\OneDrive\Documents\PowerShell\Microsoft.PowerShell_profile.ps1 -> D:\dotfiles\powershell\Profile.ps1
Installed stub at C:\OneDrive\Documents\PowerShell\profile.ps1 -> D:\dotfiles\powershell\Profile.ps1

Done. Restart pwsh to verify.
```

Open a **new** pwsh window — the error should be gone.

The installer is idempotent. Re-running it is safe and is the right thing to do whenever the error reappears (for example, if something recreates a symlink at one of the `$PROFILE` paths).

## What `install.ps1` does, step by step

For each of the two profile paths it cares about — `$PROFILE.CurrentUserAllHosts` (`profile.ps1`, loaded by every host) and `$PROFILE.CurrentUserCurrentHost` (`Microsoft.PowerShell_profile.ps1`, loaded by the current host only) — it:

1. Ensures the parent directory exists, creating it if necessary.
2. Inspects whatever is at the target path:
   - If it's a **reparse point** (symlink/junction/etc.): deletes it. Symlinks have no content, so nothing is lost.
   - If it's a **real file** (someone authored a profile manually): renames it to `<name>.bak-<yyyyMMdd-HHmmss>` so it isn't silently clobbered.
3. Writes the two-line stub above. The `D:\dotfiles\…` path inside the stub is derived from `$PSScriptRoot`, so the script keeps working if you clone the repo somewhere other than `D:\dotfiles`.
4. Prints a green `Installed stub at <dest> -> <source>` line.

It uses `$ErrorActionPreference = 'Stop'` and `-LiteralPath` everywhere so paths with spaces or `[`/`]` are handled correctly.

The script is small and safe to read in full: [`powershell/install.ps1`](../install.ps1).

## Verifying the fix

After running the installer:

```powershell
# Both targets should be plain files, not reparse points.
Get-Item -Force $PROFILE.CurrentUserAllHosts, $PROFILE.CurrentUserCurrentHost |
    Select-Object FullName, Attributes, LinkType | Format-List
```

Expected output:

```
FullName   : C:\OneDrive\Documents\PowerShell\profile.ps1
Attributes : Archive
LinkType   :

FullName   : C:\OneDrive\Documents\PowerShell\Microsoft.PowerShell_profile.ps1
Attributes : Archive
LinkType   :
```

Key things to check:

- `Attributes` does **not** contain `ReparsePoint`.
- `LinkType` is empty.
- Opening a new pwsh window no longer prints the error.
- Profile-defined commands work, e.g. `Get-Command vsc, dni, cc`.

## Troubleshooting

### "I ran the installer but the error still appears."

Make sure you opened a **new** pwsh window after running it. The currently-open session was loaded before the fix ran and still has the failed `$PROFILE` path baked in.

If the new window still errors, run:

```powershell
Get-Item -Force $PROFILE.CurrentUserAllHosts, $PROFILE.CurrentUserCurrentHost |
    Select-Object FullName, Attributes, LinkType
```

If `Attributes` still shows `ReparsePoint`, the installer didn't replace it — most often because the path is open in another process. Close that process (commonly Windows Terminal preview tabs) and rerun the installer.

### "Windows PowerShell 5.1 is also affected."

Windows PowerShell 5.1 uses a different `$PROFILE` folder (`WindowsPowerShell\` instead of `PowerShell\`), so it's usually unaffected. If you do see the same error there, run the installer from `powershell.exe` and it will install stubs at the 5.1-specific paths too.

### "I want to keep my custom profile content as well."

The installer renames any pre-existing real file to `<name>.bak-<timestamp>` rather than deleting it. Open the `.bak` copy, copy whatever you want into `D:\dotfiles\powershell\Profile.ps1` (the file the stub loads), and delete the `.bak` when you're done.

### "I don't want OneDrive backing up my Documents at all."

That's an alternative fix, but it's a system-level change with broader consequences (other apps lose their OneDrive backup). The stub approach is intentionally chosen so the existing OneDrive setup keeps working.

## References

- The error originates from PowerShell's `MountPoint`/`ReparsePoint` traversal guard, introduced to prevent cloud-sync agents from being able to swap files PowerShell is about to load. It can fire on any cmdlet that performs path resolution, not just on profile load.
- Related Microsoft Learn entries on `$PROFILE` location, including its behavior under Folder Redirection and OneDrive Known Folder Move.
- Earlier discussion in this repo: the deleted `install.ps1` (commit `483188002a01`) created the symlinks; the new `install.ps1` ([`powershell/install.ps1`](../install.ps1)) replaces them with stubs.
